# firmware/ - FirmGen (Action)

The ESP32 firmware is **generated by CraftifAI FirmGen v0.4.1 from the PRD in this folder**. Nothing here is hand-written firmware. The PRD is the source of truth.

| File | What |
|---|---|
| [prd/WildGuard_PRD.md](prd/WildGuard_PRD.md) | The PRD you upload to FirmGen (pin map, MQTT contract, species profiles, state machine, 30 requirements with acceptance criteria) |
| `frozen_requirements.*` | Export of the reviewed, **frozen** requirement set from FirmGen (add on the day) |
| `traceability_report.*` | FirmGen traceability report: requirement to code to tests (add on the day) |
| `design_document.*` | FirmGen design document (add on the day) |
| `evidence/` | UART monitor captures, acceptance results, photos and videos of the board |

The generated ESP-IDF project lives in its **own Git repository**, pushed from FirmGen's Git view (for example `wildguard-firmware`). Link it here once created:

## Workflow (Track B requirements)

1. **Prerequisites.** Install FirmGen v0.4.1 and confirm it uses ESP-IDF v5.5. Use a data-capable USB cable. Check that the board is detected and that flash plus monitor work with the lab sample.
2. **Upload the PRD.** Upload `prd/WildGuard_PRD.md`. Use the **Category-wise Manual Review** path, so judges can see the requirements were reviewed.
3. **Review and freeze.** Check every generated requirement:
   - Explicit ones should map 1:1 to the IDs in section 8 of the PRD.
   - Inferred ones: keep the sensible ones (for example the FreeRTOS task split) and reject wrong inferences.
   - Make sure the MQTT bridge requirement (detections topic in, ACK out) is present. That is the Closed Loop requirement.
   - **Freeze** the set. Take a screenshot and export it to `frozen_requirements.*`.
4. **Configure secrets** in `idf.py menuconfig` (WildGuard menu): Wi-Fi SSID and password, broker URI `mqtt://<laptop-ip>:1883`. Do not commit `sdkconfig` with secrets (see the repo .gitignore).
5. **Implement, build, flash, monitor** in FirmGen.
6. **Generate** the requirement-linked unit tests (section 10 of the PRD lists the pure functions), the design document and the **traceability report**. Export them here.
7. **Acceptance on hardware.** With the board online and the FirmGen monitor open:
   ```bash
   python tools/hil_acceptance.py --target esp32
   ```
   The script checks 19 automatic scenarios tagged with PRD requirement IDs. It writes `docs/evidence/acceptance_results.md` and `.json`, and prints the physical checks to film. Save the UART log of the same run to `evidence/uart_acceptance.log`.
8. **Push** the FirmGen project through its Git view.
9. **Bonus, Live Intelligence:** only after everything above passes. Enable Telemetry in FirmGen, which rebuilds and reflashes. Re-run step 7 to show it still passes, then show the RTOS / System Monitor during the demo.

## Rules that keep FirmGen load-bearing

- Do not hand-patch around FirmGen. Fix the PRD or the requirement and regenerate, so the traceability report stays true.
- After any edit, rebuild inside FirmGen so tests and traceability are regenerated.
- If the board misbehaves but `tools/esp32_sim.py` works with the same broker, the problem is in firmware or Wi-Fi, not in the pipeline, bridge or dashboard.
